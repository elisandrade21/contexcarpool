# Protocol: checking LLM-written rationales on the phone (fixed before any model call)

Date: 23/11/2026. Decided with the Fable plan of the same day. Any change after the first model call goes to "Deviations".

## Question
Can the phone accept a rationale phrased by a language model only when every number, rank, comfort level, booking mode, rule and percentile it states matches the facts the phone recomputed, and otherwise fall back to the rule-derived rationale?

## Sample
600 offers drawn from the 6,600 offers of the 90 check searches, stratified by search (6–7 per search; seed 20261123). For each offer the phone engine (Oxigraph 0.5.13, same files as the paper) gives: position in the search, number of offers, S, f_C, f_K, f_B, comfort level, the rule that inferred it, the price percentile, booking mode, seats, price per km, and the trade-off and its rule if any.

## Model
claude-haiku-5-5 through the Anthropic API, temperature 0, max 150 output tokens. Prompt: the offer's facts as a PROV-O-style trace (no free text from us beyond the instruction), and "write one or two plain sentences telling a passenger why this offer is at this position; use only the facts given". Prompt text and model id are stored with the outputs.

## Checker (deterministic; JavaScript for the phone and an independent Python version)
A text passes only if all of the following hold:
1. Every number in the text equals one of the given facts or the public weights (0.4, 0.2, 40%, 20%), at the precision written in the text (a number written with d decimals must equal the fact rounded to d decimals).
2. Every rule identifier (R1–R15) equals the comfort rule or the trade-off rule.
3. A stated comfort level (very comfortable, comfortable, bearable, uncomfortable; longest match first) equals the inferred level.
4. A stated booking mode (automatic/instant vs. manual/approval) equals the offer's mode.
5. "cheapest" requires percentile ≤ 25; "most expensive" or "priciest" requires percentile ≥ 75.
If a text fails, the phone shows the rule-derived rationale instead.

## Measures
- M1: share of model texts that fail the check (unsupported statement), with a 95% Wilson interval.
- M2 (negative control): the 600 rule-derived rationales must all pass.
- M3 (positive control): one scripted error injected into each rule-derived rationale (number changed, rank changed, comfort level swapped or booking mode flipped, in rotation): all 600 must fail.
- M4: 100 texts that the model rewrites with one subtle factual error on request; report how many fail the check, as measured.
- M5: added time per 100 offers for the checker in the phone engine's runtime (Node, same machine).
- M6: Python and JavaScript checkers agree on every text of M1–M4.

## Inclusion rule
The result goes into the paper only if M2 = 600/600 pass, M3 = 600/600 fail and M6 = 100% agreement. Otherwise, or if the work exceeds 8 hours, the paper is submitted without it. M1 and M4 are reported as measured, whatever they are.

## Limits stated in advance
The checker covers numbers, rules, comfort, booking and price-extreme words; not tone, causal wording or omissions.

## Deviations
D1 (23/11, before any model call): the first checker version passed 28 of the 600 injected errors, because a wrong number happened to equal another fact of the same offer (e.g., a wrong percentile equal to the position), and the two checkers disagreed on 2 texts because Python rounds half to even and JavaScript half up. Fix in both versions: numbers that follow a role word (percentile, rank/position, of N offers, score, seats, per km, currency) must equal that fact; both round half up. After the fix: M2 600/600 pass, M3 600/600 fail, agreement 1,200/1,200. The pass/fail rules were not otherwise changed.
D2 (23/11, AFTER the model outputs were seen): the role parser read model phrasing the rule-template controls never exercised, so 577 of 600 model texts failed for parser reasons, not for false facts (e.g., "24th percentile" read as a position, "score of 8.04" read as "of 8 offers", the legend "(1 = cheapest)" that our own prompt supplied, offer ids, "10 out of 10", component scores called "score", negated extremes such as "not among the cheapest"). Fix, applied identically to both checkers and to nothing else: those phrasings are parsed by role or stripped. After the fix the controls still give M2 600/600 pass, M3 600/600 fail, and agreement 1,200/1,200 (controls) and 700/700 (model texts). Because this fix was made after seeing the outputs, every remaining flagged text and every unflagged subtle-error text was inspected (see llm_result.json and llm_subtle_classified.json), and the paper reports the rate before and after the fix.
D3 (23/11, BEFORE any call to the second model): second model, claude-sonnet-5-5 (same API, effort low, same two prompts, same 600 offers and the same 100 subtle-error offers). The checker is frozen at its post-D2 version (checker.py and checker.mjs as committed); no change of any kind is allowed after its outputs are seen. Measures M1, M4, M6 as above; every flagged text and every unflagged subtle-error text is inspected and classified (false fact vs. parser artifact). Purpose: test whether the D2 parser fixes generalise to a model whose texts were never seen. Cost cap US$ 5; outputs in out/llm_generated_sonnet.json and out/llm_result_sonnet.json.
